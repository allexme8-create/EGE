# Архитектура сервиса «Обзвон+»

## Общая схема

```
Браузер (SPA без сборки)
   │  JSON/HTTP
   ▼
FastAPI (run.py, app/api.py)
   ├── CallEngine  ── CampaignRunner (поток на кампанию)
   │      ├── очередь контактов (SQLite, статусы)
   │      ├── диалог: озвучить вопрос → записать ответ → распознать → разобрать
   │      ├── AtModem (AT-команды) + AudioIO (ALSA arecord/aplay)
   │      └── DemoEmulator (без оборудования)
   ├── ASRService: Vosk | whisper.cpp | HTTP | stub
   ├── TTSService: Piper | espeak-ng (+ WAV к вопросу)
   ├── Exporting: XLSX (ручной OOXML) | CSV | JSON | расшифровки
   └── SQLite (WAL): кампании, вопросы, контакты, звонки, ответы, события, стоп-лист
```

## Модель данных

* `campaigns` — сценарий и параметры обзвона (приветствие, таймауты, повторы, режим).
* `questions` — вопросы кампании с порядком, типом, вариантами, аудиофайлом.
* `contacts` — клиенты кампании: имя, телефон (E.164), статус
  (`pending → calling → done | no_answer | failed | refused | dnc`), число попыток.
* `calls` — попытки дозвона: исход, длительность, расшифровка, запись, движок.
* `answers` — ответы: исходный текст ASR, нормализованное значение и отображение,
  уверенность, метод (`asr`/`dtmf`/`manual`), флаг «проверен», путь к записи.
* `events` — журнал (для интерфейса и разбора инцидентов).
* `do_not_call` — стоп-лист номеров.
* `settings` — настройки поверх значений по умолчанию из `app/config.py`.

Таблица ответов — это `contacts ⋈ answers` по вопросам кампании, поэтому она всегда
актуальна и не требует отдельной денормализации.

## Жизненный цикл звонка (режим модема)

1. `CampaignRunner` берёт следующий `pending`-контакт (пропуская стоп-лист и учитывая
   разрешённые часы звонков).
2. `ATD+7…;` — набор номера. Ответ модема `CONNECT`/`VOICE CALL: BEGIN` = абонент снял
   трубку; `BUSY`/`NO CARRIER` = занято/не ответил (с учётом повторов).
3. Озвучивание приветствия и вопроса: готовый WAV → `aplay`, иначе синтез (Piper/espeak)
   и конвертация в 8 кГц mono (`ffmpeg`).
4. Запись ответа `arecord` c VAD: остановка через 1,6 с тишины или по `max_seconds`.
   Параллельно собираются DTMF (`+DTMF: 1`), если абонент нажал клавишу.
5. ASR (`asr/__init__.py`) → текст; `answers.parse_answer` → значение для таблицы.
6. `INSERT INTO answers` + расшифровка в `calls.transcript`; переход к следующему вопросу.
7. `ATH` — отбой. Контакт получает `done`; при отказе («не звоните») — `refused`
   и номер попадает в `do_not_call`.

## Разбор ответов

`app/answers.py` — набор правил, не зависящих от ASR:

| Тип вопроса | Примеры фраз | Результат |
|---|---|---|
| да/нет | «да, конечно», «нет, спасибо», «не интересует» | `yes` / `no` |
| отказ | «не звоните мне больше», «уберите из списка» | `refused` → стоп-лист |
| выбор | «вариант два», «мне нужна связь», «телевизор» | номер + текст варианта |
| оценка | «пять», «на пятёрку», «4» | `5` / `4` |
| число | «сорок два», «35 минут» | `42` / `35` |
| свободный | любая фраза | текст целиком |

Правила приоритетны: отказ важнее «да/нет»; явные отрицания («не интересует»,
«пока нет») распознаются отдельно. Уверенность < `min_confidence` → ответ
подсвечивается в интерфейсе для ручной проверки. Повторный разбор сохранённых
расшифровок — `POST /api/answers/recalc` (например, после улучшения словаря).

## Расширение

* **Пул модемов**: `CallEngine` уже изолирует устройство (`audio_io()`, `get_modem()`).
  Чтобы звонить параллельно, создайте `N` раннеров с разными портами и настройкой
  `max_concurrent_calls`, распределяя контакты по `contacts.id % N`.
* **Другой транспорт**: реализуйте интерфейс из `engine._modem_call`
  (dial/play/record/hangup) поверх SIP/GSM-шлюза — остальной код не меняется.
* **Другой ASR**: добавьте класс с `available()`/`transcribe()` в `app/asr/__init__.py`.
* **СУБД**: `app/db.py` — тонкая обёртка; при переходе на PostgreSQL замените
  `sqlite3` на пул соединений (SQL-схема почти совместима).
